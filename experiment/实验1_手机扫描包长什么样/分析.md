# 实验 1：原始手机扫描包究竟是什么

这里的“原始”是指**分享出的 ZIP 没有再做电脑端建模**，不是指手机没有计算。手机采集时已经运行 ARKit/RoomPlan：深度和相机跟踪会形成空间网格，RoomPlan 会生成墙、窗、家具类别和尺寸，App 可即时显示 Mesh、RoomPlan、Coverage、Photo 等预览。手机上看到完整的彩色 3D，并不意味着 ZIP 中存在一份训练好的高斯泼溅。

## 两份包的实际内容

| 项目 | Office.zip，第一次 | Office 2.zip，第二次 |
| --- | ---: | ---: |
| ZIP 文件项 | 1,364 | 867 |
| 原始照片 | 56 | 37 |
| 深度帧 | 434 | 274 |
| RoomPlan 墙 / 窗 / 物体框 | 7 / 1 / 6 | 6 / 1 / 5 |
| `rooms/room-0.usdz` | 有 | 有 |
| `mesh/room-0.ply` | **没有** | **有：98,553 点、176,922 面** |
| `.splat/.ksplat/.sog` | 未发现 | 未发现 |

共同的核心文件是 `manifest.json`、`rooms/room-0.json`、`rooms/room-0.usdz`、`photos/photos.json`、`depth/frames.json`，以及目录内的 JPEG、Float16 深度和置信度文件。RoomPlan JSON 给的是**结构参数和物体边界**；USDZ 是手机可看的 RoomPlan 导出；第二包的 PLY 是采集得到的三角网格。第一包没有 PLY，所以不能把它的点图称为“原始完整网格”。

实验 1 的点图只选 12 帧深度，用相机内参和每帧位姿将有效像素稀疏投影成约 32,131 / 33,070 个显示点。这是为快速检查准备的轻量抽样，不表示 ZIP 只有 12 帧或深度信息不完整：原包分别记录了 434 / 274 帧深度、置信度、相机内参与位姿。全帧重建留给实验 4。点图没有完成多帧融合、遮挡去除、表面封闭或照片纹理。深度热图是按距离着色的展示图，颜色不代表现场真实材质。

## 为什么手机里的画面可能更“完整”

App 的 Photo 模式可把已有照片映射到扫描网格的三角面上；Coverage、Clay、Mesh 和 RoomPlan 模式则强调不同证据层。显示方式和导出文件不是一对一关系。第一次 ZIP 缺少 PLY 的**原因尚未确定**；现有证据只允许确认“此包没有这个文件”，不能推断手机当时没有实时网格或把它说成导出丢失的确定故障。

若你看到的确是独立的 3DGS 预览，需要检查对应 App/版本的实际导出格式或训练链。当前这两份 ZIP 和本地基线源码不足以把手机画面判定为高斯泼溅。实验页面故意把“原始 PLY 顶点”“稀疏深度点”和“高斯泼溅”分开标注。

可核对：`../.private/summary.json`、各包的 `source/Room/`，手机项目的 `HouseCapture/PreviewScene.swift` 与 `PhotoTextures.swift`。私有抽样资产只在本机使用。
